# IDE Agent 执行开发任务 · 通用提示词模板

---

## 使用说明

这是四份文档体系中的**第三份**，生成顺序为：

```
整体开发文档 → 模块级开发文档 → 代码实现（本模板） → 独立验收（04）
```

**前置条件**：模块文档已生成，且 `progress.md` 中该模块为「📝 文档已生成」。

**原则**：严格按模块文档与全局契约编码；技术栈以文档为准，不预设语言或框架。收尾只标 🔍 待验收，**禁止自标 ✅**（✅ 仅 04 写入）。

**棕地修补请勿用本模板当入口**：模块已 ✅ 之后的增量走 [`specs/SDD-GUIDE.md`](../../specs/SDD-GUIDE.md)（任务包 → IDE 单线编码自验 → HITL）。本模板专供绿场 03。

将下方提示词复制给 IDE Agent 即可。路径均相对 **`docs/` 文档根**；若工作区是仓库根则加前缀 `docs/`（详见 [00-overview.md](./00-overview.md) §二）。

## 提示词正文

```
你是一名资深全栈工程师。技术栈以项目文档为准（overall-design.md / global-contract.md / 本模块开发文档）。
请按步骤完成本模块代码实现。

【确认节奏（自动化优先，降低阻塞）】
- 纯实现步（脚手架、数据模型、数据访问、业务逻辑、接口暴露、客户端）做完即继续，**不打断**；每步在回执中简述改动即可。
- **高风险项（显式枚举，遇任一必须暂停等确认，不得自判为低风险）**：
  1. 改动跨模块共享入口（桌面主进程、全局路由注册、打包配置、CLI 入口）
  2. 数据模型大改（删字段、改类型、破坏兼容的迁移）
  3. 删除或废弃已有对外接口
  4. 引入文档/契约未列的新依赖（含新的第三方 SDK）
  5. 任何架构级偏离（技术栈、部署形态、进程模型变更）
  6. 修改 global-contract.md 中已锁定且被其他模块依赖的定义
- 上述清单为**穷举式门控**：仅当命中清单才阻塞；未命中即视为低风险、连续推进。不得为省事把命中项也连过，也不得把未命中项擅自升级为高风险来打断流程。
- 若维护者不在，流程可继续推进所有低风险实现步；仅高风险项排队等待，不假借自治越过架构边界。

---

【读取文档】
- explanation/overall-design.md（上下文与技术栈，不必精读全部细节）
- reference/global-contract.md（必须遵守）
- reference/modules/Fxx-*.md（编码唯一依据；按 progress.md 中「📝 文档已生成」确定文件名）
读完输出摘要：技术栈、模块职责、数据实体、接口列表、依赖模块；确认后再列疑问。

---

【当前项目状态】
- 自行读取目录结构；无代码则进入脚手架步骤
- 自行判断已完成模块；若为首个模块注明「无已有代码」

---

【代码规范】
1. 遵守全局契约中的字段、响应、错误、路径等约定，不得擅自修改
2. 禁止占位实现；每个对外行为须有完整实现
3. 不引入模块文档未列的新依赖；需要则先说明等确认
4. 按全局约定统一处理错误/异常
5. 注释语言与项目约定一致（无约定则用中文）
6. 默认不改本模块以外代码；模块文档明确要求改动的共享入口（如桌面主进程、全局路由注册、打包配置）可以改，但须事先说明
7. 接口层只做校验与委托；业务逻辑在业务层
8. 跨端字段命名遵循契约
9. 优先简单可靠方案；契约要求的可替换抽象须实现，不算过度设计
10. 客户端代码遵循项目既有框架与目录约定；类型与请求走统一封装
11. 语言版本与特性以 overall-design.md 为准，不得擅自降级或换栈
12. 存储实现（含特殊检索语法）严格按模块文档的 Schema/查询示例，不得改用其他存储或方言

---

【开始前：疑问与建议】
1. 列出文档歧义及推荐方案
2. 有多方案时做简要对比并推荐

建议默认采纳：列出后执行文档回写，再开始编码。
高风险项（架构、数据模型大改、删除已有接口）须标「⚠️ 高风险，请确认后再执行」，等回复。

【文档回写】
建议导致文档需改时，先回写再编码：

层级 1 — 模块文档：接口签名、数据模型、枚举、路径、通信方式、核心流程等
  注释格式：<!-- 回写修正：{Agent建议|我指示}…，原因… -->

层级 2 — 全局契约：跨模块类型、命名、通道/事件、错误约定等；递增版本号并在变更日志留痕，同时在 progress.md 备注列记录

层级 3 — 不回写：纯实现细节（异步手段、局部命名、缓存库选择等）

回写后告知改动，再编码。事后异议则回滚该回写并按指示重做。

---

【开发步骤】
默认连续推进（纯实现步不打断）；每步在回执简述改动。仅「高风险项」完成后暂停等确认（见上方确认节奏）。不适用则跳过并说明原因。

第一步：环境与脚手架
- 脚手架符合已确认技术栈；依赖安装与构建/启动通过
- 存储可连通（若使用）
- 契约与当前代码不冲突
- 特殊运行时（如桌面内嵌服务）按整体设计做连通性检查
- 无代码时：按整体设计从零搭建，确认可运行后再继续
- 有已有代码时（存量项目预检）：
  · 确认现有目录结构与模块文档第 8 节文件清单的映射关系
  · 识别可复用的公共组件与工具函数（模块文档第 2 节已列出），确认其接口未变
  · 检测已有测试框架与运行方式，后续测试须遵循同一约定
  · 扫描潜在冲突（同名路由、同表字段、同事件名），有冲突先报告等确认
- 问题必须先修复

第二步：数据存储变更（若涉及）
- 完整 Schema/DDL/迁移（含索引与注释）

第三步：数据模型
- 实体/模型、枚举、入参出参；公共类型标记是否写入契约

第四步：数据访问
- 按项目约定的数据访问方式实现；含复杂查询

第五步：业务逻辑
- 完整实现（事务与错误处理按项目约定）

第六步：接口暴露
- 校验 + 调用业务层
- 实时接口若文档要求：按契约实现完整生命周期，不得敷衍

第七步：客户端 / 界面（若涉及）
- 类型、请求封装、状态、页面/视图、路由
- 桌面窗口与 IPC（若文档要求）按清单实现；改共享入口须符合规范第 6 条

第八步：自查

| 检查项 | 状态 | 备注 |
|-------|------|------|
| 各接口 | ✅/⚠️/❌ | |
| 各页面/视图（如有） | ✅/⚠️/❌ | |
| 实时 / 桌面（如有） | ✅/⚠️/❌ | |
| 业务规则 | ✅/⚠️/❌ | |
| 全局契约 | ✅/⚠️/❌ | |
| 与文档技术栈一致 | ✅/⚠️/❌ | |
| 安全自查项（对应模块文档第 7 节） | ✅/⚠️/❌ | 输入校验/越权/敏感数据/注入 |
| 测试覆盖（对应模块文档第 10 节） | ✅/⚠️/❌ | 各层用例是否通过 |
| 存量代码无破坏（若适用） | ✅/⚠️/❌ | 已有测试是否仍通过 |

第九步：收尾更新（以实际落地回写文档；行为仍以文档为准）
1. progress.md → 🔍 待验收，填编码完成时间；备注可写「交 04」——**不得**写 ✅
2. global-contract.md 按实际落地追加本模块契约，递增版本号（+0.1）并在变更日志追加一行
3. 后续模块注意事项（如有）
4. 将自查表与改动文件清单一并交 04 验收
告知改了哪些文件。

---

【注意】
- 难点先讲思路再写代码
- 出错先分析再改，禁止盲目改动
- 纯实现步可连续推进但每步回执留痕；高风险项必须暂停确认，不得连过
- 禁止自行将 progress 标为 ✅
```

## 分步追加提示词（按需使用）

### 遇到 Bug 时

```
不要急着改代码。
先分析可能原因（高→低），给出最可能的 1–2 个及验证方法。
确认后只做最小修改，并说明改动位置、原因与影响面。
```

### 代码偏离文档时

```
停下，重读开发文档【指定章节】。
当前实现与【指定描述】不符，偏差是【…】。
按文档重做，不要保留旧思路。
```

### 代码审查时

```
对照模块文档审查：
1. 接口是否齐、入参出参是否一致
2. 校验是否到位
3. 业务规则是否体现
4. 错误处理是否遗漏
5. 跨端字段是否对齐
6. 重复与可复用点
7. 是否遵守 global-contract.md
8. 实时/桌面相关是否按文档完整实现（如有）
9. 是否与已确认技术栈一致
10. 安全自查项（第 7 节）是否逐条落实
11. 测试用例（第 10 节）各层是否覆盖

| 检查项 | 状态 | 问题 | 修复建议 |
```

### 解释代码时

```
说明：设计原因、潜在风险、若需求变为【…】需改哪里。
```

### 回滚时

```
回滚到上一步完成状态：删除本步新建文件，恢复被改文件，并列出回滚内容。
```

### 发现文档或设计级问题时（跨阶段升级）

```
停下当前编码。问题超出本步回滚范围，需要升级处理：

问题描述：【…】
影响范围：【仅本模块 / 涉及其他模块 / 涉及整体架构】
建议回退到：【模块文档阶段 / 整体设计阶段】

请确认回退目标。确认后我会：
1. 将 progress.md 中本模块状态改为 ⏸️ 阻塞，备注列注明原因
2. 若涉及契约变更，在 global-contract.md 变更日志记录「编码阶段发现设计缺陷」
3. 列出需要重新生成的文档清单
```

### 验收打回时（接 04 独立验收的结论）

```
收到 04 验收打回清单。按清单逐项修复，**不自行判定「已差不多」**，严格对齐模块文档第 11 节验收标准：

修复项：
| 序号 | 打回项 | 修复方式 | 对应代码位置 |
|------|--------|---------|------------|
| 1 | | | |

修复完成后：
1. 重跑本模块测试（模块文档第 10 节用例）确保无回归
2. 若打回涉及契约/文档，先回写 global-contract.md / 模块文档（按层级 1/2 规则）再改码
3. 将代码与回执交 04 重新验收（仅重验变更项 + 影响面）

注意：打回期间 progress.md 维持 ⏸️ 阻塞（或 04 标记的待验收态），修复通过后才由 04 标 ✅。
不打回清单当作已通过——04 未确认前不得自行标 ✅。
```

## 使用技巧

**疑问前置 + 建议默认采纳 + 文档先回写再编码**，可减少方向性返工。

**高风险才打断。** 纯实现步连续推进，回执留痕即可定位；只有穷举清单里的高风险项才显式暂停。

**收尾按实际代码回写契约**（反映落地事实），但行为标准仍以文档为准；progress 只标 🔍，版本号必须递增。

**按 progress 顺序推进**；当前模块须经 04 标 ✅ 后，再启动下一模块的 02/03。

**技术栈以文档为准**，换栈属高风险，须先改文档并确认。

**安全自查项逐条过。** 第八步自查表中的安全行不是摆设——对照模块文档第 7 节的自查清单逐项确认，有「涉及」标记的项必须在代码中有对应实现。

**存量代码改前先跑测试。** 若项目已有测试套件，第一步预检时先跑一遍确认基线绿色；收尾自查时再跑一遍确认无回归。

**问题超出本步就升级。** 发现模块文档或整体设计有误时，不要试图在代码里"绕过去"，用跨阶段升级提示词走正式回退流程。

**收尾 ≠ 验收通过。** progress 只标 🔍；须交 04。禁止在回执里写「验收通过 / ✅」。
