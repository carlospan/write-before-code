# 生成整体开发文档 · 通用提示词模板

---

## 使用说明

这是四份文档体系中的**第一份**，生成顺序为：

```
整体开发文档（本模板） → 模块级开发文档 → 代码实现 → 独立验收
```

**适用场景**：已有完整 PRD，需要据此生成整体开发文档（架构、模块拆分、全局约定）。

**何时不必跑本模板（绿场轻量档）**：`overall-design.md` / `global-contract.md` / `progress.md` **已经存在**，本模块不改架构，且维护者明示「走轻量档」→ 跳过 01，直接用 [02-module-spec.md](./02-module-spec.md)。新项目第一次、或模块拆分/技术栈有变，仍须跑本模板（可做增量修订，不要另起炉灶装没看见）。

**原则**：以 PRD 为唯一需求来源与约束来源；技术选型、接口约定、目录结构均服从 PRD。PRD 未写明处，在理解摘要中给出建议并经确认后再写入正式文档。本模板不预设任何语言、框架或产品形态。

**生成后会输出**：
1. `explanation/overall-design.md`
2. `reference/global-contract.md`（初始化）
3. `reference/progress.md`（初始化）

将下方提示词复制给 **架构师阶段** 的 Agent 即可。路径均相对 **`docs/` 文档根**；若工作区是仓库根则加前缀 `docs/`（详见 [00-overview.md](./00-overview.md) §二）。

## 提示词正文

```
你是一名资深全栈架构师。请严格以本项目 PRD 为准，生成高质量的整体开发文档。
该文档用于后续拆分模块级开发文档，并最终供 IDE Agent 据此编码。
给出清晰的架构方向与模块边界即可，字段与接口细节留给模块级文档。
（文中 explanation/、reference/ 路径均相对 docs/ 文档根。）

---

【PRD 需求文档】
- 本项目 PRD 路径：explanation/PRD.md（若不存在，向维护者确认实际路径）
- 若该文件仍是落点说明、或正文明显属于上一项目，停止并向维护者确认，**禁止**自行编造需求
请先读取**本项目 PRD**，并输出需求摘要：项目定位、核心功能、技术栈与约束、目标用户、非功能要求。
确认无误后再继续。
若 PRD 未明确技术栈或关键约定，须在理解摘要中给出推荐及理由，等我确认后再写入正式文档。

---

【第一步：输出理解摘要，等我确认后再继续】
1. 项目核心定位（一句话）
2. 功能模块初步划分（按依赖给出建议开发顺序编号）
3. 用户与权限：多用户则说明角色与权限边界；单用户则注明并说明配置如何管理
4. 技术栈：PRD 已指定则复述并做合理性检查；未指定则给出推荐及理由（语言/框架/数据存储/构建与包管理及主要版本）
5. 关键架构决策建议（部署形态、服务拆分、是否需要异步/队列等——仅针对本项目实际需要）
6. 范式识别：仅当 PRD 涉及以下情形时列出——桌面/嵌入式运行时、实时通信、常驻后台任务、可切换的外部服务等；不涉及则写「无特殊范式」
7. PRD 中不明确或需要补充之处
8. PRD 自身风险评估（质疑 PRD，而非只复述）：
   - 可行性：核心技术需求是否有已知不可行/极高风险处（性能、合规、第三方依赖可用性）
   - 一致性：PRD 内部是否自相矛盾（功能间冲突、范围与资源不匹配）
   - 范围漂移风险：是否隐含"范围蔓延"触发点（如"等一下还要加…"）
   - 若评估发现重大风险，须在确认摘要中显式标出并建议缓解或待确认，不得静默带过
9. 存量代码检测：读取项目目录，判断是否已有代码库。若有，简述现有目录结构、技术栈、公共组件与测试现状，评估与 PRD 要求的差异及接入策略；若无则注明「全新项目」

我确认后再生成完整文档。

---

【第二步：生成整体开发文档】
按以下结构生成。与本项目无关的章节写「本项目不涉及」并简述原因，不得跳过标题。
凡规范类内容：PRD 已有定义则直接采用并引用；PRD 未定义则给出可落地的约定草案，且须与已确认技术栈一致。

1. 项目概述
   - 定位与核心价值
   - 目标用户与使用场景
   - 功能模块一览（按开发顺序）：

   | 开发顺序 | 功能模块 | 模块职责简述 | 覆盖 PRD 条目 |
   |---------|---------|------------|------------|
   | 1 | （根据 PRD 填入） | （一句话） | （PRD 中的功能编号/段落，如 F-1、F-3） |

2. 技术架构
   - 整体架构图（ASCII：客户端/服务端/存储/外部依赖及通信方式）
   - 运行时与部署：进程或服务如何划分、如何启动与通信；非标准部署（如桌面内嵌后端）须写清进程模型与端口绑定
   - 技术选型表（层级 / 选型 / 版本 / 理由；与已确认技术栈一致）
   - 外部依赖清单（用途；若有成本或备选方案一并注明）

3. 模块拆分方案
   - 模块表：开发顺序 / 模块名 / 职责 / 前置依赖
   - 依赖关系图（ASCII）
   - 核心数据流图（ASCII：数据载体与触发时机）
   - 拆分依据

4. 角色与权限总览
   - 按 PRD：有则列表说明；无则注明「本项目不涉及」

5. 数据存储设计总览
   - 核心实体清单（名称 + 用途 + 所属模块）；非关系型则用该存储的对应概念
   - 实体间核心关联
   - 不写完整字段（留给模块文档）；若 PRD 已有结构则引用并做合理性审查

6. 全局技术规范（后续模块必须遵守；内容以 PRD 为准，未定义处经确认后定稿）
   仅展开本项目需要的条目；不需要的写「本项目不涉及」：
   - 接口约定：统一成功/失败响应形态、错误码或错误表示方式、路径与版本策略（一律采用 PRD 已有定义；PRD 未定义时再拟定）
   - 安全与鉴权边界（按 PRD：多用户鉴权，或单机/本地通信边界等）；须覆盖以下维度（按项目实际裁剪）：
     · 鉴权模型：认证方式、会话/令牌机制、权限粒度（RBAC/ABAC/简单角色）
     · 输入校验：全局校验策略（白名单/类型约束/长度限制），防注入与 XSS 基线
     · 数据隔离：多租户或用户间数据隔离边界
     · 敏感数据：加密存储、传输加密、日志脱敏、密钥轮换策略
     · 通信安全：TLS 要求、本地通信边界（如桌面 IPC 的访问控制）
   - 命名约定（存储 / 后端 / 前端；有差异时说明转换）
   - 分页与列表约定（若项目有列表接口）
   - 日志与可观测性约定
   - 目录与模块组织约定（符合已确认技术栈惯例）
   - 实时通信约定（仅当范式识别涉及）
   - 外部服务集成约定（仅当需要可切换或隔离第三方依赖时：抽象边界、超时重试降级、密钥不入仓）
   - 后台任务约定（仅当有常驻/定时任务时）
   - 敏感配置与密钥管理（仅当 PRD 或合规要求涉及）

7. 环境与配置管理
   - 开发环境要求
   - 环境变量与配置分区
   - 构建、分发、更新（仅当 PRD 涉及）

8. 非功能性要求
   - 摘自 PRD：性能、安全、稳定性、国际化等；PRD 未提则注明「PRD 未要求」或给出最低建议供确认
   - **量化基线须进契约**：将性能（延迟/吞吐）、稳定性（可用性/错误率）、安全基线（加密/审计）等可量化项提炼为具体数值，写入 global-contract.md 的「非功能基线」段（见第三步），避免各模块自由表述导致跨模块不可对齐

9. 开发顺序
   - 唯一推荐顺序；同一时间只推进一个模块：文档完成 → 编码完成 → 下一个
   - 表：顺序 / 模块名 / 前置依赖 / 理由
   - 基础与被依赖模块在前；可延后功能排在后部
   - progress.md 必须与此顺序一致

10. 风险与待确认事项
    - PRD 歧义、选型权衡、技术难点与应对思路

11. 阶段回退与升级机制
    - 模块文档阶段发现整体设计缺陷（如模块拆分不合理、技术选型需调整）：
      · 暂停当前模块文档生成，标记为「⏸️ 阻塞」
      · 输出问题描述与影响范围，由我决策是否回退修改 overall-design.md
      · 修改后更新契约版本并在变更日志注明「架构修订」
    - 编码阶段发现模块文档或整体设计有误：
      · 小范围（接口签名、字段调整）：IDE Agent 按文档回写机制处理
      · 大范围（模块职责变更、拆分调整）：暂停编码，回退到模块文档阶段重新生成
    - progress.md 状态回退规则：✅ → 📝（需重新编码）或 📝 → ⬜（需重新生成文档），回退时在备注列注明原因与日期

---

【第三步：生成配套文件】

1. reference/global-contract.md（初始化）
   - 从第 5、6 节提炼跨模块必须统一的约定
   - 包含：实体清单（暂无字段）、接口与错误约定、命名、分页（如有）、以及本项目实际启用的实时/外部服务/任务/密钥等约定
   - **非功能基线段**（从第 8 节提炼量化值）：延迟/吞吐/可用性/错误率/安全基线等可量化项，作为跨模块对齐锚点
   - 标注「各模块契约待模块文档生成后逐步补充」
   - 文件头部建立版本与变更日志：

     # 全局契约

     > 契约版本：v1.0 | 基线日期：{生成日期}

     ## 变更日志

     | 版本 | 日期 | 变更摘要 | 触发模块 |
     |------|------|---------|---------|
     | v1.0 | {日期} | 初始化：从整体设计提炼全局约定 | — |

   - 后续每次模块文档生成或代码回写导致契约变更时，追加一行日志并递增版本号（小版本 +0.1）

2. reference/progress.md（初始化）
   - 按开发顺序列出全部模块，状态均为「⬜ 未开始」

     # 开发进度记录

     | 开发顺序 | 模块名称 | 状态 | 文档路径 | 覆盖 PRD 条目 | 完成时间 | 备注 |
     |---------|---------|------|---------|------------|---------|------|
     | 1 | （填入） | ⬜ 未开始 | - | （PRD 条目） | - | - |

   - 状态五种：⬜ 未开始 / 📝 文档已生成 / 🔍 待验收 / ✅ 已完成 / ⏸️ 阻塞（需回退或等待决策）
   - ✅ 仅由 04 验收通过后写入；01 初始化时全部为 ⬜

---

【约束条件】
- 一切以 PRD 为准；不得引入 PRD 未要求且未经确认的技术栈、中间件或规范
- 技术选型、目录结构、示例语法必须与已确认技术栈一致
- 本文档不展开模块级字段与接口细节
- 禁止占位符（「此处省略」「待定」等）；不适用则写「本项目不涉及」
- 使用 Markdown；代码块标明实际语言

---

【输出要求】
直接写入对应目录并告知已生成文件：
1. explanation/overall-design.md
2. reference/global-contract.md
3. reference/progress.md
```

## 使用技巧

**源头质量决定后续成本。** 生成后优先核对：技术栈是否与 PRD/确认一致；模块边界与依赖是否合理；第 6 节是否只包含本项目真正需要的约定；开发顺序是否可执行。

**第 10 节风险项尽早拍板**，避免开发中途改架构。

**按顺序推进，契约只追加。** 一次一个模块；模块经 04 验收 ✅ 后契约与代码对齐；后续模块只追加、不破坏已完成模块所依赖的定义。

**特殊形态单独复核。** 若 PRD 含桌面运行时、实时通信或常驻任务，确认对应章节有实质约定，而非一笔带过。

**高敏感项目做威胁建模。** 若涉及支付、医疗、个人隐私等高敏感域，第 6 节的安全五维度检查清单不够，须补充 STRIDE 级威胁建模（数据流图 + 每项威胁的缓解），而非仅填检查项。

**契约版本必须递增。** 每次契约变更（无论来自模块文档还是代码回写）都须在变更日志追加记录。版本号是跨文档对齐的锚点，跳过会导致后续模块比对失效。

**存量项目先摸底再动手。** 若理解摘要第 9 点检测到已有代码库，优先确认现有目录结构与技术栈是否可复用；不可复用则在第 2 节明确迁移策略，避免模块文档阶段才发现冲突。

**回退不可怕，悄悄偏移才可怕。** 发现设计缺陷时走第 11 节的回退机制，更新 progress 状态与契约版本；禁止在不改文档的情况下直接改代码"将就"。
