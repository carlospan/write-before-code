# Docs-driven development · reusable workflow template (Diátaxis + SDD)

> **write-before-code** — English docs tree.  
> Other language: [中文](../zh/README.md) · Skill entry: [SKILL.md](../../SKILL.md)

This directory is a **reusable docs + Agent pipeline template** for:

1. **Greenfield**: From PRD through 01→02→03→04, produce design, contract, module specs, and acceptable implementation (**the same IDE Agent can run them in order**). When 01 artifacts already exist and this module does not change architecture, the maintainer may explicitly take the **lightweight track** (skip 01; still must run 02→04)  
2. **Brownfield / iteration**: After code exists, use `specs/` (**incremental Spec**, IDE single-line; close the loop by writing `INDEX.md` then archiving — do not delete working drafts)

Docs follow the [Diátaxis](https://diataxis.fr/) four quadrants; `specs/` is the SDD extension.

**Usage**: Copy this directory (or use it as `docs/`) into a new repo → write that project’s `explanation/PRD.md` → follow [00 overview](./how-to/agent-prompts/00-overview.md). Not bound to a specific product or stack.

The current workspace treats this directory as the docs root. If nested in a larger repo, see the repo-root README for engineering bootstrap (omit the link if none exists).

## ★ HITL iron rule (must read)

> **How to lock requirements with AI, then write code — this is not a chat habit; it is a formal workflow.** (Product-agnostic.)

| Name | Meaning |
|------|------|
| **HITL (human in the loop)** | Key product decisions need **maintainer approval**; the Agent must not lock them in unilaterally |
| **Spec-driven** | Write observable behavior into the spec first (greenfield module docs / brownfield task packs), then code |
| **Incremental consensus (agree one slice at a time)** | **Confirm only one small slice at a time**; write to disk as soon as agreed (greenfield: understanding summaries / module docs; brownfield: task packs) — do not batch until the end, and do not treat chat history as the source of truth |

One sentence: **Incremental consensus under HITL + Spec-driven.**  
Dedicated page: [how-to/hitl-alignment.md](./how-to/hitl-alignment.md) · authoritative detail: [specs/SDD-GUIDE.md](./specs/SDD-GUIDE.md) **§2.5**

## Dual paths (how to choose)

```text
Greenfield full track (new project / architecture undecided)
  PRD → 01 → 02 → 03 → 04
  Artifacts: explanation/ + reference/

Greenfield lightweight track (01 artifacts exist, this module does not change architecture, maintainer must say so)
  02 (lightweight) → 03 → 04
  Module doc still required; ✅ still belongs to 04

Brownfield (patches / evolution after a module is ✅)
  specs/tasks task pack (incremental Spec) → IDE code + self-verify → (optional acceptance record) → archive/
  When touching the contract, write back reference/global-contract.md (version +0.1)
```

## Recommended reading path

**Greenfield: start a new project with this template**

1. [how-to/agent-prompts/00-overview.md](./how-to/agent-prompts/00-overview.md)  
2. Write [explanation/PRD.md](./explanation/PRD.md) (section structure: see “Step 2” in [01-overall-design.md](./how-to/agent-prompts/01-overall-design.md))  
3. Full track 01 → 02 → 03 → 04, one module at a time; lightweight conditions in [00 §3](./how-to/agent-prompts/00-overview.md)  

**Brownfield: existing code, behavior must change**

1. [specs/SDD-GUIDE.md](./specs/SDD-GUIDE.md) (includes **§2.5 incremental consensus**)  
2. Copy [specs/tasks/_template.md](./specs/tasks/_template.md) → IDE: agree one slice at a time, fill HITL → after coding authorization, self-verify → maintainer HITL → write `INDEX.md` from [`_index-template.md`](./specs/archive/_index-template.md) then move to archive (no INDEX → must not move)  

**After 01/02 produce artifacts (greenfield lookup)**

1. `explanation/PRD.md` → `explanation/overall-design.md`  
2. `reference/global-contract.md` + `reference/progress.md`  
3. When coding a module, open `reference/modules/Fxx-*.md`

## Path rules (when Agents read/write docs)

Full discipline: [00 overview · path rules](./how-to/agent-prompts/00-overview.md).

| Current workspace | How to write doc paths |
|-----------|----------------|
| `docs/` itself | `explanation/PRD.md`, `specs/tasks/…` |
| Repo root (docs under subdirectory `docs/`) | `docs/explanation/PRD.md`, `docs/specs/…` |

Engineering code paths are relative to the repo root; do not resolve doc paths relative to `how-to/agent-prompts/`.

Requirements recognize only `explanation/PRD.md`. If that file is still a placeholder, or its body belongs to a previous project, do not start 01.

## Classification principles (when writing new docs)

| If the content is mainly… | Put it in… |
|--------------|---------|
| Guiding the reader through a controlled learning journey | `tutorials/` |
| “To achieve X, follow these steps” | `how-to/` |
| Fields, paths, error codes, schemas, inventories | `reference/` |
| Background, motivation, trade-offs, concept clarification | `explanation/` |
| Iteration task packs, receipts, acceptance, archive | `specs/` |

Module `Fxx` docs are mostly **encodable specs** → `reference/modules/`. Extract large “why” passages into `explanation/`.
