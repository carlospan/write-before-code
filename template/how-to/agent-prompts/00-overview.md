# Agent 文档驱动开发体系 · 总纲

> 本文件是 `agent-prompts/` **四份**提示词（01 整体设计 / 02 模块文档 / 03 IDE 编码 / 04 独立验收）的**入口与总纲**，并说明与 **`specs/` 棕地旁路** 的关系。  
> 先读本文件，再按需要打开对应分册或 [specs/SDD-GUIDE.md](../../specs/SDD-GUIDE.md)。

---

## 一、这套体系解决什么问题

把「从需求到可运行代码 / 从变更到可验收修补」切成**阶段清晰、文档落盘、可验收**的流水线。

核心假设：**AI 编码最容易犯的错，是「为了跑通悄悄偏离规格」**。整套机制都在对抗这一个错。

**默认执行者**：维护者指定的 **IDE Agent** 在同一产品里按序跑阶段（换提示词 / 换阶段心态）。

### 双路径总览

```
【绿场 · 满配】新项目 / 架构未定（同一 IDE Agent 按序换提示词）
PRD（explanation/PRD.md）
  │  [01 · 架构师阶段]
  ▼
explanation/overall-design.md
reference/global-contract.md      （契约版本锚点）
reference/progress.md             （模块状态机）
  │  [02 · 架构师阶段，逐模块]
  ▼
reference/modules/Fxx-{模块}.md
  │  [03 · 工程师阶段]
  ▼
代码 + 契约回写；progress → 🔍 待验收
  │  [04 · 验收阶段：换「验收心态」再跑一遍，或维护者亲自验]
  ▼
模块 ✅ → 下一模块

【绿场 · 轻量档】01 产物已在，且本模块不改架构（须维护者明示）
  跳过 01 → 02（轻量）→ 03 → 04
  仍须落盘模块文档；✅ 仍归 04 / 维护者

【棕地】模块已 ✅ 之后的修补 / 演进（IDE 单线）
specs/tasks/任务包（增量 Spec）
  │  有疑先问维护者
  ▼
IDE 编码 + 工程自验（+ 可选回执）
  │  维护者 HITL / 可选验收记录
  ▼
迁入 specs/archive/（不删）
动契约 → 同步 global-contract（+0.1）
```

**绿场铁律**：整体设计 → 模块文档 → 代码 → **独立验收过一遍**。满配不得跳步把未落盘的架构写进代码；轻量档跳过 01 须四条件同时满足且维护者明示，不算跳步。不得以 03 自查代替 04 / 维护者。  
**棕地铁律**：先短规格再大改码；自验 ≠ HITL 通过；详见 [SDD-GUIDE](../../specs/SDD-GUIDE.md)。  
**人机协作铁律（通用）**：HITL + Spec-driven + **渐进对齐（一块一拍）**——产品边界未清时一次只确认一小块，谈定立刻落盘。见 [hitl-alignment.md](../hitl-alignment.md) · [SDD §2.5](../../specs/SDD-GUIDE.md)。

### 不可变原则（Agent 先读这一份）

细则分散在后文与旁路文档；下列条目**不可自行放宽**。违反即流程事故。

| # | 原则 | 细则 |
|---|------|------|
| 1 | 需求只认当前项目 `explanation/PRD.md`（须已写入正文） | §二、§四.1 |
| 2 | 先落盘再大改码；聊天不是真源 | §四.9 · [hitl-alignment.md](../hitl-alignment.md) |
| 3 | 一次一个焦点（绿场一个模块 / 棕地一个任务包） | §四.4 |
| 4 | 契约每次变更必须版本递增并写日志 | §四.3 |
| 5 | 03 禁止自标 ✅；绿场 ✅ 仅 04 或维护者 | §三、§五 |
| 6 | 高风险穷举项必须停；不得自判为低风险连过 | §四.6 |
| 7 | 假绿无效：真跑测试 + 非空壳断言 | §四.10 |
| 8 | 有代码后改行为：先改规格再改码 | SDD-GUIDE §三 |
| 9 | 棕地 Spec 用增量（ADDED / MODIFIED / REMOVED），验收用 WHEN/THEN | SDD-GUIDE §1.1 |
| 10 | 未拍板的产品 / 架构大转向，Agent 不得自治宣布新开阶段 | §六 |

## 二、文档路径规范

分册正文里的路径写成 `explanation/...`、`reference/...`、`specs/...`，语义相对 **文档根 `docs/`**，**不要**相对 `how-to/agent-prompts/` 解析。

| 当前工作区 | 读写时实际使用的前缀 |
|------------|---------------------|
| 工作区就是文档根本身（目录名常为 `docs/`） | 直接用下文路径 |
| 是仓库根，且文档在 `docs/` 子目录 | 所有文档路径前加 `docs/` |
| 文档根目录名不是 `docs` | 先向维护者确认，禁止猜 |

代码、测试、工程配置相对**仓库根**。

### 绿场流水线 I/O

| 阶段 | 角色 | 读 | 写 |
|------|------|----|----|
| — | 维护者 | — | `explanation/PRD.md` |
| 01 | 架构师 | PRD | `overall-design.md`；`global-contract.md`；`progress.md` |
| 02 | 架构师 | 01 三份 + PRD | `modules/Fxx-*.md`；增量 contract / progress（→ 📝） |
| 03 | 工程师 | 设计 + 契约 + 本模块文档 | 代码（仓库根）；回写 contract 与模块文档（层级 1）；progress → 🔍（禁止 ✅） |
| 04 | 验收 | 模块文档 + 契约 + 代码 | progress → ✅ 或 ⏸️；**不改规格正文**（不合格则升级 02 / 01，不派 03 补文档） |

### 棕地流水线 I/O

| 阶段 | 角色 | 读 | 写 |
|------|------|----|----|
| 立项 / 规格 | IDE Agent | 相关模块文档 / 契约 / 代码 | `specs/tasks/YYYY-MM-DD-*.md`（可选 `-方案.md`） |
| 编码 | IDE Agent | 任务包 | 代码；可选 `-回执.md` |
| HITL | 维护者 | 回执 / diff / 观感 | 拍板；可选 `-验收记录.md` |
| 归档 | IDE / 维护者 | — | 写 `INDEX.md` 后迁入 `specs/archive/YYYY-MM-DD-主题/` |

**需求只认**当前项目 `explanation/PRD.md`。落点说明未写入正文、或正文属于上一项目时，不得开 01。

### 落盘纪律

1. 绿场**文档**只许落在 explanation / reference 上表路径：01 写 overall-design / 契约 / progress；02 写 Fxx + 增量契约 / progress；03 写代码（仓库根）并回写契约 / 模块文档 / progress（🔍）；04 **只改** progress（✅ / ⏸️），不改规格正文。  
2. 棕地过程稿只许落在 `specs/tasks/`（归档进 `specs/archive/`；桶内必须有 `INDEX.md`）。  
3. 模块文档命名：`F{两位}-{英文名}.md`。  
4. **不预建空壳**：overall-design / global-contract / progress / Fxx 由 01 / 02 **直接创建**完整文件。  
5. 写错目录视为流程事故：挪回并删误建文件。

## 三、绿场四阶段

| 分册 | 阶段心态 | 输入 | 输出 | 关键门控 |
|------|----------|------|------|---------|
| 01 | 架构师 | PRD | overall-design / global-contract / progress | 理解摘要先确认 |
| 02 | 架构师 | 整体设计 + 契约 | `Fxx-*.md` + 更新契约 / 进度 | 理解摘要 + **契约比对**（轻量档：摘要 ≤ 5 条，比对只列触及项） |
| 03 | 工程师 | 模块文档 + 契约 | 代码 + 回写契约 / 模块文档；progress → 🔍 | 高风险项确认 + 自查表 |
| 04 | 验收 | 模块文档 + 契约 + 代码 | 验收结论；progress → ✅ 或 ⏸️；不改规格正文 | 按模块文档第 11 节；虚则回 02 |

**默认可由同一 IDE Agent 按序执行**（换提示词 / 换阶段，不要跳过落盘）。

### 绿场轻量档（跳过 01）

**同时满足**才可走；缺任一条则走满配 01→04。Agent **不得自行宣布**轻量档。

| 条件 | 要求 |
|------|------|
| 01 产物已在 | `overall-design.md`、`global-contract.md`、`progress.md` 均存在且为当前基线 |
| 本模块不改架构 | 不换技术栈 / 进程模型 / 模块拆分 / 跨模块依赖图 |
| 顺序合法 | 按 progress 取下一 ⬜ 模块，前置均为 ✅ |
| 维护者明示 | 口头或书面「走轻量档」 |

轻量档仍须：02 生成完整 12 节标题的 `Fxx-*.md`（无关节写「本模块不涉及」+ 一句原因）；理解摘要 ≤ 5 条；契约比对只列本模块触及的约定；第 11 节用 WHEN/THEN；然后 03 → 04。**不减 04，不自标 ✅。**

若做着发现要改架构：停，回 01 增量修订 overall-design / 契约，再继续。

**边界红线**：

- 架构决策只在 01 / 02 落盘之后才进 03；03 不得自行改未文档化的架构、技术栈、数据模型。  
- 03 只实现，不定义「该做什么」。  
- 04 只验收，不编码、不改规格正文（progress ✅ / ⏸️ 除外）；代码不符打回 03，规格不合格升级回 02 / 01。**✅ 仅 04 过一遍或维护者**，03 禁止自标 ✅。  
- **禁止未落盘设计就直接写实现**（可在同一会话内 01→确认→02→确认→03，但每阶段必须先写完文档）。

## 四、全局纪律（绿场 + 棕地一律适用）

1. **需求源清晰**：绿场以当前项目 `explanation/PRD.md` 为准（须已写入正文，不得用落点说明或上一项目需求）。棕地以任务包 Spec + 既有契约 / 模块文档为准。  
2. **权威分态**：绿场（尚无代码）以文档为准；**有代码后**可观测行为以代码 + 测试为准，改行为必须先改规格再改码（见 SDD-GUIDE §三）。  
3. **契约版本必须递增**：`global-contract.md` 每次变更 +0.1 + 变更日志。  
4. **一次一个焦点**：绿场一次一个模块（前置 ✅）；棕地一次一个任务包。  
5. **禁止占位符**：不适用写「本项目不涉及」，不得删模块文档规定标题。  
6. **确认门控分级**：01 / 02 理解摘要、02 契约比对必过；03 / 棕地编码纯实现步可连推，**高风险穷举项**必须停。  
7. **回退是流程不是失败**：设计缺陷走回退 / 升级，禁止悄悄偏移。  
8. **验收独立过一遍**：绿场 04（换验收心态再跑或维护者）/ 棕地 HITL；编码阶段自查不能代替。  
9. **过程落盘**：规格、回执、验收写成文件，不靠聊天传长文；棕地默认薄稿（见 SDD-GUIDE）。  
10. **假绿无效**：须真跑测试 + 非空壳断言。

## 五、状态机与验收

```
⬜ 未开始 → 📝 文档已生成 → 🔍 待验收 → ✅ 已完成
任意态 → ⏸️ 阻塞（须落到终态，备注原因）
```

| 状态 | 谁写入 |
|------|--------|
| ⬜ / 📝 | 01 / 02 |
| 🔍 | 03（禁止 ✅） |
| ✅ | **仅 04 / 维护者** |
| ⏸️ | 发现方；须再落到终态 |

棕地任务**不**用本状态机替代模块行；任务闭环见 `specs/archive/`。

03 自查不能代替验收。04 按模块文档第 11 节核对，并**优先机检**（测试 / lint / diff / 红线）。通过才标 ✅。同一 IDE Agent 做 04 时须**换验收心态**（只核对、不改码、不改规格正文），或由维护者亲自验。分册：[04-accept.md](./04-accept.md)。棕地验收见 SDD-GUIDE §2.4 与任务包验收栏。

## 六、反模式与边界

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 未落盘就让编码阶段定架构 | 跨模块不一致 | 架构只在 01 / 02 落盘后进 03 |
| 为跑通悄悄偏离文档 | 规格脱钩 | 先回写再改码 |
| 跳过契约版本递增 | 比对失效 | 每次 +0.1 + 日志 |
| 03 自标 ✅ | 自验自 | 只标 🔍；04 / 维护者才 ✅ |
| 把空壳 PRD / 上一项目需求当输入 | 做错产品 | 仅当前项目 `explanation/PRD.md` |
| 方向未想清就开码 | 错误进实现 | 先短规格 + 有疑先问 |
| 为仪式凑齐全套过程附件 | 吞吐崩、上下文偏差 | 棕地 IDE 单线 + 薄落盘（附件按需） |
| 并行推进多模块 / 多架构包 | 契约冲突 | 一次一个 |
| 假绿 | 行为未落地 | 真跑测试 + 非空壳 |
| 编码方自判「是否高风险」越权 | 越界 | 高风险穷举清单；触及 HITL 就问 |
| 未获明示就跳过 01 | 架构悄悄漂 | 轻量档须维护者宣布；否则满配 |

本体系**明确不支持**：

1. **多模块并行开发**（绿场）：须一次一个；需并行请另选方案。  
2. **生产灰度 Schema 迁移**：02 覆盖新库 DDL，不覆盖灰度剧本。  
3. **第三方 API 版本漂移回流**：项目应在 overall-design / 契约自补钉死策略。  
4. **以可执行 Schema 为唯一权威**：本体系以自然语言规格承载「为什么」；OpenAPI 等可并存，须自行映射。  
5. **未拍板的产品 / 里程碑大转向**：须维护者 HITL，Agent 不得自治宣布「新开阶段」。

## 七、交付判定与自动化

绿场出口：

1. 全部模块 ✅，顺序与 overall-design 一致。  
2. global-contract 无未决变更，版本连续。  
3. 每模块经 04 独立验收（或维护者签字）。  
4. 整体回归测试全绿。  
5. PRD 核心功能可溯源到模块文档 / 代码。

棕地无「整仓交付」概念；以任务验收记录 + 契约同步为准。

自动化约定：

1. 确认门控：纯实现连推；高风险穷举才阻塞。  
2. 验收：先机检后人判。  
3. 工程仓应固化测试套件与 lint 的跑法；建议 CI：死链、测试、lint；文档侧接 [`specs/ci-probes.md`](../../specs/ci-probes.md)（参考实现 `ci-probes-reference.py`）。  
4. 建议：契约版本连续性自检（探针 P1）。
