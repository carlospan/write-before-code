# 生成模块开发文档 · 通用提示词模板

---

## 使用说明

这是四份文档体系中的**第二份**，生成顺序为：

```
整体开发文档 → 模块级开发文档（本模板） → 代码实现 → 独立验收
```

**前置条件**：
- `explanation/overall-design.md`
- `reference/global-contract.md`
- `reference/progress.md`

**原则**：以 PRD、整体设计与全局契约为准。DDL、类型、路径、实现要点一律按已确认技术栈书写，不套用其他语言或框架的习惯写法。

**生成后会输出**：
1. `reference/modules/F{两位编号}-{模块英文名}.md`
2. 更新 `reference/global-contract.md`（本模块增量）
3. 更新 `reference/progress.md`（本模块 → 📝 文档已生成）

**轻量档**（须维护者明示，见 [00-overview §三](./00-overview.md)）：01 产物已在且本模块不改架构时，仍用本模板，但理解摘要 ≤ 5 条、契约比对只列本模块触及项；12 节标题不得删，无关节写「本模块不涉及」+ 一句原因。第 11 节仍须 WHEN/THEN。之后照常 03 → 04。

将下方提示词复制给 **架构师阶段** 的 Agent 即可。路径均相对 **`docs/` 文档根**；若工作区是仓库根则加前缀 `docs/`（详见 [00-overview.md](./00-overview.md) §二）。

## 提示词正文

```
你是一名资深全栈架构师。请根据项目整体设计与全局契约，为指定模块生成可直接供 IDE Agent 编码的模块开发文档。
字段、接口、业务规则必须精确到可生成代码；语法与结构必须与已确认技术栈一致。

---

【前置文档读取与一致性校验】
- explanation/overall-design.md
- reference/global-contract.md（必须遵守）
- reference/progress.md
读取后理解：整体架构、已确认技术栈、已有契约、当前进度。
记录当前契约版本号（global-contract.md 头部「契约版本：vX.X」），后续本次更新基于此版本递增。
若 global-contract.md 与 progress.md 均标注了契约基线版本且二者不一致，停止并提示我先对齐；若尚未建立基线版本号，跳过此项并在本次契约更新时补上。

---

【本模块信息】
目的：为本模块生成开发文档
选择规则：按 progress.md 开发顺序，取「⬜ 未开始、且前置依赖均为 ✅ 已完成」的下一个模块（若需指定，替换下一行）
模块名称：按上述规则自动判断
档位：满配（默认）/ 轻量档（仅当维护者明示，且 01 产物已在、本模块不改架构）
  - 轻量档：理解摘要不超过 5 条；契约比对只列出本模块实际触及的约定行；12 节标题仍全
特殊要求：无（有则注明，如实时流式、外部服务、桌面窗口、后台任务等——须与 PRD/整体设计一致）

---

【第一步：输出理解摘要，等我确认后再继续】
1. 核心职责（一句话）
2. 涉及的数据实体（名称、主要字段、与已有实体关系）
3. 主要接口列表及大致数量（按本项目实际接口形态：HTTP / RPC / CLI / 事件等）
4. 对已有模块的依赖（调用什么、复用什么）
5. 技术难点（如有）
6. 本模块技术栈要点（从 overall-design.md 复述，不自行发挥）
7. 整体设计中对本模块描述不清之处

确认后再做契约比对。

---

【第二步：契约比对，等我确认后再生成文档】
将本模块设计与 global-contract.md 比对，输出表。范围按本项目实际启用的约定裁剪：

1. 数据实体：字段名/类型/默认值/空约束
2. 已有模块对外接口：参数与返回类型（枚举须用契约定义，不用裸字符串）
3. 枚举：值集合完全一致；新增须先改契约
4. 错误表示：不与已有错误码/错误类型冲突，符合全局分段或分类约定
5. 接口路径或路由：符合全局路径/命名约定
6. 若项目启用了实时通道、IPC 等：新增名称不与契约冲突

| 比对项 | 契约定义（章节与行号） | 本模块设计 | 结果 |
|--------|----------------------|-----------|------|
| … | … | … | 一致 / 差异→以契约为准 |

「契约定义」列须标注章节与大致行号，证明已读原文而非凭记忆。
有差异一律以契约为准。契约有遗漏则先补契约再写模块文档，并在第 12 节列出本次补充。
**契约冲突仲裁**：若本模块设计揭示既有契约定义之间矛盾（如 A 模块契约与 B 模块契约对同一概念定义不一致），不得自行择一，须暂停并列出冲突双方原文与影响范围，交维护者拍板（或回退 01 修订整体设计）。契约冲突属架构级问题，不在模块文档阶段静默解决。

---

【第三步：生成模块开发文档】
按以下结构生成；无关章节写「本模块不涉及」，不得删标题。

1. 模块定位
   - 职责与在项目中的位置
   - **覆盖的 PRD 条目**（编号/段落，与 overall-design.md 开发顺序表的「覆盖 PRD 条目」列对齐；多模块共担同一条目须注明各自负责部分）
   - 核心业务流程（ASCII）
   - 数据流（上下游；简单则可并入流程图）

2. 依赖的已有模块与存量代码适配
   - 正向依赖：依赖谁、具体用什么
   - 反向影响：是否需改已有代码/配置；有则逐项写清影响评估；无则注明不涉及
   - 存量代码适配（若项目非全新）：
     · 已有目录结构与本模块文件清单的映射关系
     · 可复用的公共组件、工具函数、中间件（列出路径与用途）
     · 已有测试框架与用例组织方式，本模块测试须遵循同一约定
     · 潜在冲突点（如已有同名路由、同表字段、同事件名）及规避方案

3. 数据存储设计
   - 完整 Schema / DDL / 迁移说明（语法符合已选存储）
   - 字段用途注释；类型、约束、默认值写全
   - 索引或检索设计及理由
   - 结构变更须给出变更语句或迁移步骤
   - 仅当本模块需要向量/全文等特殊检索时，补充类型、度量、索引与查询示例（方言以所选存储为准）

4. 类型定义（本模块新增）
   - 后端：持久化模型、入参、出参（与存储字段对应；语法按已确认后端语言）
   - 前端或其他客户端：按项目约定的类型系统书写（无前端则注明不涉及）
   - 枚举（如有）
   - 标明哪些需进入全局契约

5. 状态与规则（如有）
   - 离散状态：状态值、流转图、各状态允许操作
   - 评分/规则驱动：输入因素 → 决策 → 动作；附流程
   - 皆无则注明不涉及

6. 接口详细设计
   - 总览表（方法或操作名 / 路径或标识 / 说明 / 鉴权要求）
   - 每个接口：入参、成功响应（遵循全局响应约定说明业务数据部分）、失败响应
   - 列表/分页遵循全局约定
   - 实时接口（仅当涉及）：事件类型、载荷、连接生命周期、分块与结束约定
   - 不涉及则注明

7. 核心业务逻辑
   - 关键操作步骤
   - 边界与异常
   - 数据隔离或权限规则（如适用）
   - 安全与性能自查（按本模块实际涉及裁剪，不涉及则注明）：
     · 输入校验：哪些入参需校验、校验规则（类型/范围/格式/长度）
     · 越权防护：哪些操作需校验资源归属或角色权限
     · 敏感数据：本模块是否涉及敏感字段，存储/传输/日志中如何处理
     · 注入防护：拼接查询/命令/模板的位置及防护手段
     · 并发与幂等：写操作是否需幂等设计或乐观锁
     · 性能边界：大数据量场景的分页/限流/缓存策略；慢查询风险点

8. 服务端实现要点
   - 拟创建文件清单（完整路径，符合目录约定）
   - 复用的既有能力
   - 难点方案（推荐 + 备选）
   - 禁止事项（如不得改其他模块、不得擅自加依赖）
   - 后台任务（仅当涉及）：触发、生命周期、对外状态、与全局任务约定的关系
   - 外部服务（仅当涉及）：依赖抽象边界、配置与密钥来源、超时重试降级（引用全局约定）

9. 客户端 / 界面实现要点（按项目形态：Web / 桌面 / 其他）
   - 页面或视图、路由、关键交互、状态管理要点
   - 桌面窗口 / IPC / 系统集成（仅当涉及）
   - 无界面则注明不涉及

10. 测试策略与用例
    - 测试分层（按项目已有测试框架；无框架则注明「手动验证为主」，用例仍须列全）：
      · 单元测试：纯业务逻辑、工具函数、状态流转、规则计算——不依赖外部服务
      · 集成测试：数据访问层（含复杂查询与事务）、模块间接口调用、外部服务 mock
      · 接口/端到端：每个对外接口至少 1 正常 + 1 异常；涉及鉴权则补越权用例
      · **契约测试**：按 global-contract.md 的接口/错误/枚举/路径约定写自动断言，确保本模块实现不偏离契约——这是契约版本化机制的可机检延伸，跨模块回归时尤其有效
    - 正常 / 异常流程表（标注每条用例所属层级）
    - 涉及实时或后台任务时补相应场景（连接断开重连、任务超时/重试/取消）
    - 安全相关用例：注入尝试、越权访问、敏感数据泄露检查（对应第 7 节自查项）
    - 性能基线（若第 7 节识别了性能风险点）：给出可量化的响应时间或吞吐量预期

11. 验收标准
    - 每条必须可外部判定。禁止「功能正常」「体验良好」「按预期工作」
    - 默认句式：WHEN <条件> THEN <可观测结果>（EARS）；也可用 Given / When / Then
    - 每条须对应第 10 节至少一条测试；确实只能人判的，单列并写明为何不能机检
    - 示例：WHEN 未登录用户请求受保护接口 THEN 返回 401 且不泄露资源是否存在

12. 文档生成后需更新
    - 追加到 global-contract.md 的内容，并递增契约版本号（+0.1）、在变更日志追加一行（版本/日期/变更摘要/触发模块）
    - progress.md：本模块 → 📝 文档已生成

---

【约束条件】
- 命名、类型、响应与错误约定以全局契约为准，不得擅自改已有定义
- 禁止占位符；无关写「本模块不涉及」
- 路径、错误表示遵循整体设计与契约
- Markdown；代码块标明实际语言

---

【输出要求】
保存到 reference/modules/，命名：F{两位编号}-{模块英文名}.md（编号与 progress 开发顺序对齐，英文名用短横线）。
同时更新 reference/global-contract.md 与 reference/progress.md，并汇总改动说明。
```

## 进度记录格式参考

```markdown
# 开发进度记录

| 开发顺序 | 模块名称 | 状态 | 文档路径 | 覆盖 PRD 条目 | 完成时间 | 备注 |
|---------|---------|------|---------|------------|---------|------|
| 1 | （模块名） | ✅ 已完成 | reference/modules/F01-example.md | F-1 | YYYY-MM-DD | 04 验收通过 |
| 2 | （模块名） | 🔍 待验收 | reference/modules/F02-example.md | F-2 | - | 03 编码完成 |
| 3 | （模块名） | 📝 文档已生成 | reference/modules/F03-example.md | F-3 | - | - |
| 4 | （模块名） | ⬜ 未开始 | - | F-4 | - | - |
```

- ⬜ 未开始 → 📝 文档已生成 → 🔍 待验收 → ✅ 已完成
- ⏸️ 阻塞：设计缺陷回退或验收打回时标记，备注列注明原因与回退目标
- 选下一模块：前置依赖须均为 ✅（仅 📝 / 🔍 不够）

## 使用技巧

**先确认理解，再比对契约，最后写文档。** 两道关可拦下大部分跨文档不一致。

**严格按 progress.md 顺序**，一次一个模块。顺序与依赖冲突时以依赖为准并回写顺序。

**契约更新必须落地**，否则下一模块会重复或冲突定义。每次更新递增版本号并写变更日志，这是后续模块比对的锚点。

**精度标准（可操作判定）**：以「编码前疑问预算」衡量——IDE Agent 开工前就本模块文档提出的澄清疑问 **≤ 3 条** 视为达标；超过则判文档不达标，回退本模块文档补充而非让编码 Agent 硬猜。涉及实时、桌面或后台任务时，通道名、事件与生命周期必须写死，不能一笔带过。疑问预算超限时，02 应补完文档再交 03，而非依赖 03 边问边做。

**测试分层要写清归属。** 每条用例标注属于单元/集成/端到端哪一层，IDE Agent 才能据此选择正确的测试方式，避免把该 mock 的依赖真连了。

**安全自查不是走形式。** 第 7 节的自查项直接对应第 10 节的安全用例；如果自查写了「涉及」但测试用例里没有对应条目，说明文档自相矛盾。

**第 11 节必须可判定。** 04 只核 WHEN/THEN（或等价勾选）；写虚了会被打回补文档，而不是让编码方「看着用」。

**存量项目重点看第 2 节。** 已有代码库的复用清单和冲突规避方案写清楚，IDE Agent 才不会重复造轮子或踩到已有逻辑。
