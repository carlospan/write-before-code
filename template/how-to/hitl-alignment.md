# 人机协作铁律 · 渐进对齐（一块一拍）

> **定位**：与具体产品无关的**通用需求工作流**。本模板复制到任意仓库的 `docs/` 后默认采用。  
> **细则权威**：[`../specs/SDD-GUIDE.md`](../specs/SDD-GUIDE.md) **§2.5**；入口亦见 [`../README.md`](../README.md) 开篇 ★。

---

## 一句话

**HITL + Spec-driven 下的渐进对齐**：关键决策由人点头；先写可观测 Spec；**一次只确认一小块，谈定立刻落盘**，再编码。

这不是闲聊习惯，是正式工作流。

---

## 三个名字（对外也好说）

| 名字 | 意思 |
|------|------|
| **HITL（人在回路）** | 关键产品 / 路线决策由**维护者点头**；Agent 不擅自定死 |
| **Spec-driven（规范驱动）** | 先把可观测行为写进规格（绿场：模块文档第 11 节；棕地：任务包），再编码 |
| **渐进对齐 / incremental consensus（一块一拍）** | 一次一块；谈定立刻落盘；不攒到最后、不靠聊天记录当真源 |

近亲：敏捷 **Example Mapping**（短对话抠规则与边界）——不强制卡片仪式，只取小步对齐。  
常见 AI 口令 Plan → Confirm → Implement：此处把 Confirm **拆成多拍**，且每拍**立刻落文档**。

---

## 何时用

- 新能力 / 新模块边界未清  
- 意图怎么认、和邻能力怎么划界  
- 人格、确认策略、从宽/从慎等产品分寸  

琐碎修 bug（错字、单测断言）不必走满。

---

## 怎么做（默认节奏）

1. Agent **一次只抛一块**想法或抉择（宜短；维护者说「一次不要说太多」时必须遵守）。  
2. 维护者表态（对 / 改 / 否）。  
3. **谈定立刻落盘**——绿场写入 01 / 02 理解摘要、模块文档对应节或 HITL 表；棕地写入任务包（增量 Spec：ADDED / MODIFIED / REMOVED + WHEN/THEN 验收 + HITL 表）。需要时同步契约 / 设计文——**不攒到最后才记**。  
4. 再抛下一块；关键 HITL 齐了 → 维护者 **编码放行** → 再大改码。  
5. 编码中冒出新抉择：停，回到 1–3，不默默扩 scope。

绿场 `01→04` 与棕地 `specs/tasks` **都适用**「一块一拍」精神。**绿场最常见落点是理解摘要 / 模块文档；棕地最常见落点是任务包。** 不要在绿场尚未立项任务时为「一块一拍」单独建任务包。

---

## 反模式（视为流程违规）

- 一次抛十几条「请一起拍板」长清单  
- 聊了很多却不落盘，只靠聊天记录当真源  
- 未放行就开写实现；或放行后把「另开刀」顺手做进本包
