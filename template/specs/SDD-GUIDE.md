# SDD-GUIDE：棕地 / 迭代怎么写规格（防 drift）

> **定位**：有代码之后的 Spec-driven 流程。与绿场 `01→04` 并列，不互相取代。  
> **参考**：ThoughtWorks SDD、GitHub Spec Kit；归档不删（过程稿视为长期资产）。  
> **人机协作铁律**（与 [`../README.md`](../README.md) 开篇 ★ 同义）：**HITL + Spec-driven + 渐进对齐（一块一拍）**——详见 **§2.5** 与 [how-to/hitl-alignment.md](../how-to/hitl-alignment.md)。这是定 Spec 的默认姿势，不是可选闲聊。

---

## 一、什么时候写任务包

任何**会改对外行为 / 跨模块约定**的变更，先在 `specs/tasks/` 落任务包（用 `_template.md`）：

- Spec：可观测结果，**增量**写（当前行为 + ADDED / MODIFIED / REMOVED），不写实现细节、不重写整模块规格  
- 实现：步骤可勾选；大改动可另附可选 `-方案.md`  
- 验收：WHEN … THEN … 可勾选清单（禁止「功能正常」）  
- 契约变更：动契约则勾上并回写版本  
- HITL：哪些须维护者拍板  
- **产品边界未清时**：用 §2.5 一块一拍填满 HITL，再编码放行——**禁止**一次抛长清单、聊完不落盘  

纯错字、纯注释、已约定的格式化 → 可不建包（维护者可收紧）。

### 1.1 Spec 怎么写增量

对照代码 + 测试写「当前行为」，再用三条增量表达「目标行为」：

| 标记 | 含义 |
|------|------|
| **ADDED** | 新的可观测行为 |
| **MODIFIED** | 已有行为从 A 变为 B（必须写出 A 和 B） |
| **REMOVED** | 删掉的行为（写原因；破坏性须 HITL） |

归档时这些增量是审计线索；若动了跨模块约定，必须同时回写 `global-contract.md`，不要只把变更留在任务包里。

## 二、spec 与实现分离 + IDE 单线默认

- 先短 spec → 再实现 → 对照验收勾选 → 回写权威文档。  
- 任务闭环后**归档 `specs/archive/` 不删**。  
- `specs/tasks/` = 进行中；闭环迁 archive。

> **为何单线：** 拆成两家 Agent 时没有共享工作记忆，靠厚过程稿对齐仍易理解偏差。维护者常驻同一 IDE 时，由该 IDE Agent 一气呵成更稳。

### 2.1 默认：IDE Agent 一气呵成

| 职责 | 谁 |
|------|-----|
| 起草 / 修订任务包与实现方案 | IDE Agent（或维护者口述后落盘） |
| 落地改业务代码 / 测试 | IDE Agent |
| 工程自验（测试 / lint / 对照验收栏） | IDE Agent |
| 回写契约 / 模块文档 / progress 备注 | IDE Agent |
| 感受 / 产品 / 路线 / 破坏性契约拍板 | **维护者**（HITL） |

**纪律：**

1. **先落盘再大改码**：非琐碎改动先写/更新任务包。  
2. **有疑先问**：触及换栈、破坏性契约、产品范围大变 → 停下来问维护者。  
3. **一次一包**。  
4. **薄过程稿**：默认只要任务包本体；方案 / 回执 / 验收记录按需另附，不必凑齐全套。

### 2.2 落盘，不靠聊天传长文

- 进行中 → `specs/tasks/`  
- 闭环后 → `specs/archive/YYYY-MM-DD-主题/`（**不删**；桶内**必须**有 `INDEX.md`，从 [`archive/_index-template.md`](./archive/_index-template.md) 复制）  
- Agent **直接读目录**。

**命名**（前缀 `YYYY-MM-DD-任务名`）：

| 后缀 | 何时 |
|------|------|
| `.md`（任务包本体） | **始终** |
| `-方案.md`（可选） | 改动面大 / 要维护者先看设计 |
| `-回执.md`（可选） | 编码后留下改动与自验摘要 |
| `-验收记录.md`（可选） | 书面勾选验收栏时（维护者或 IDE） |

### 2.3 编码前自检

```
① 读代码 + 写/更新任务包（Spec / 验收 / HITL）
       ↓
② HITL：边界未清时用 §2.5 渐进对齐（一块一拍、谈定即落盘）；齐了等维护者编码放行
       ↓
③ 编码 + 测试
       ↓
④ 回写文档；需要时落盘回执；写 `INDEX.md` 后整组迁 archive
```

- 琐碎改动可跳过完整任务包，但仍须防 drift 回写。  
- 高风险 / 吃不准：维护者可要求「先只写方案、先别动码」，或**可选**请另一位审阅者 **只看一页短方案**（顾问，不默认进流水线）。  
- 「方向未想清就开码」仍是事故——用短规格 + 有疑先问 + **§2.5** 承接。  
- 产品边界未清时：优先 §2.5，不要一次抛长方案清单。

### 2.4 验收归属

| 动作 | 含义 |
|------|------|
| 工程自验 | IDE 对照验收栏（WHEN/THEN）+ 机检；**≠ 产品通过** |
| HITL / 产品验收 | 维护者；需要时可落 `-验收记录.md` |

验收栏禁止「功能正常」类不可判定句。IDE 回执禁止自标「产品验收通过 / ✅」糊弄 HITL。

### 2.5 渐进对齐（一块一拍 · HITL 对话纪律）【核心 · 必守】

**是什么：**

- **HITL**：关键决策维护者点头，Agent 不擅自定死。  
- **Spec-driven**：对齐结果写入**本任务包** Spec / HITL 表，再编码（本节管棕地；绿场落点见 [hitl-alignment.md](../how-to/hitl-alignment.md)）。  
- **渐进对齐**：一次一小块，谈定就落盘，避免长文一次灌完导致遗忘与口头漂移。  
- 近亲：Example Mapping（小步抠边界）。  
- Plan → Confirm → Implement：Confirm **多拍** + **每拍落文档**。

**一句话：** HITL + 规范驱动下的渐进对齐；不是临时闲聊，是正经需求工作流。

**何时用：** 新能力开包、确认/意图策略、与邻能力边界尚不清时。琐碎修 bug 不必走满。

**怎么做：**

1. Agent **一次只抛一块**（宜短）。  
2. 维护者表态（对 / 改 / 否）。  
3. **谈定立刻写入**任务包 Spec + HITL（及契约等）——**不攒到最后**。  
4. 关键 HITL 齐了 → **编码放行** → 再大改码。  
5. 编码中新抉择：停，回到 1–3。

**反模式（流程违规）：** 长清单一次拍；聊完不落盘；未放行就改码；顺手把「另开刀」做进本包。

**与 §2.1–2.3：** 渐进对齐是 IDE 单线里填满 HITL / 写清 Spec 的**默认手法**。专页：[hitl-alignment.md](../how-to/hitl-alignment.md)。

## 三、权威分态（绿场 vs 有代码后）

| 阶段 | 行为冲突时谁优先 | 改行为怎么做 |
|------|------------------|--------------|
| **绿场**（模块尚无代码或 03 进行中） | 以模块文档 + `global-contract` 为准 | 先回写文档再改码 |
| **有代码后**（棕地任务） | **可观测行为以代码 + 测试为准**；规格过时必须回写 | **先改规格（任务包/契约）再改码**，禁止「只改码不改文档将就」 |

禁止用「文档永远压过代码」在棕地里掩盖未回写的 drift。

## 四、防 drift

1. 改常量、默认值、公开协议、模块/文件名、功能开关 → 排查 `docs/` 写死同值处并回写。  
2. 契约变更必须 `global-contract` 版本 +0.1 + 变更日志。  
3. 验收优先机检：测试 / lint / diff 范围 / 红线 grep（项目提供 `tools/verify_*` 则调用）。  
4. 假绿无效：空壳实现、不跑的测试 → 打回。

## 五、HITL 决策路由

| 类别 | 示例 | 路由 |
|------|------|------|
| 可自治 | 起草任务包、实现细节、工程自验、落盘、常规 commit | IDE Agent |
| 须维护者拍板 | 换技术栈、产品范围大变、契约破坏性变更、是否开新里程碑、工作流改轨 | 阻塞 @维护者 |
| 异步可接受 | 文案口径、非阻塞观察项节奏 | 不卡当前包，择机拍板 |

可自治项不得悄悄改架构方向或已锁定契约；触及则升级为拍板。

## 六、与绿场 01–04 的衔接

- **新项目 / 架构未定**：走满 01→02→03→04。  
- **已有 overall-design / 契约 / progress，且本模块不改架构**：维护者可宣布 **绿场轻量档**——跳过 01，只跑 02（轻量）→ 03 → 04。细则见 [00-overview §三](../how-to/agent-prompts/00-overview.md)。  
- **模块已 ✅ 之后的增量**走本 GUIDE（任务包），不要为小修补新开 Fxx。  
- 03 绿场收尾只标 progress 🔍；✅ 仍归 04 独立过一遍或维护者——与棕地「自验 ≠ HITL 通过」同构。  

详见 [00-overview](../how-to/agent-prompts/00-overview.md)「双路径」节。
